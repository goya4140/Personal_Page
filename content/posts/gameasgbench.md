把一个游戏项目写出来，和交付一个满足需求的游戏，不是同一件事。页面能启动、代码能编译、甚至大多数检查都通过，仍然可能在一次真实的拖拽、状态重置或连续操作中失败。GameASG-Bench 试图把这条差距测出来。

本文解读 Xiuhui Zhang、Yi Chen、Shusheng Xu 等人的 **GameASG-Bench: Benchmarking Autonomous Software Generation for Game Development**，依据 2026 年 9 月 18 日提交的 [arXiv v1](https://arxiv.org/abs/2609.21293v1)。论文的核心不是提出新的游戏生成模型，而是把“行为可测试性”提前写进生成任务：Agent 除了生成游戏，还要实现一套让评测器能准备场景、发送玩家级动作、读取稳定状态并检查不变量的接口。官方代码位于 [areal-project/GameASG-Bench](https://github.com/areal-project/GameASG-Bench)。

## 一、课题解读：怎样判断 Agent 交付了一个真正可用的应用

自主软件生成希望把人的需求直接变成可执行应用。Agent 会读文件、改代码、调用工具、运行程序，再根据错误修订。对于一个完整应用，局部函数正确远远不够：输入处理、状态转移、渲染、资源变化、失败条件和重新开始必须协同工作。

游戏是研究这个问题的一个紧凑代理。它通常是自包含的，但同时包含操作、空间关系、状态机、反馈和终止条件。一个游戏“看起来能玩”并不能说明鼠标和触摸都能推动流程，也不能说明重置后旧状态不会泄漏，更不能说明一条连续操作链会到达正确终态。

因此，可靠评测需要同时回答三件事：交付物是否满足源代码层面的接口要求；真实浏览器输入是否改变了可见游戏；状态快照是否与画面和运行时行为一致。只给出一个“可玩/不可玩”标签，还不足以定位失败发生在什么需求上。

## 二、相关文献解读：从代码生成走向可验证的完整应用

| 工作 | 主要探索 | 与本篇的连接 |
| --- | --- | --- |
| [WebGameBench](https://arxiv.org/abs/2605.17637) | 通过真实浏览器交互评价浏览器原生游戏 | 说明游戏应用可以作为 requirement-to-application 的行为载体 |
| [GameCraft-Bench](https://arxiv.org/abs/2606.17861) | 要求 Agent 端到端生成可玩的 Godot 游戏，并结合回放与多模态证据 | 将完整游戏交付和可复现验证联系起来 |
| [GameGen-Verifier](https://arxiv.org/abs/2605.07442) | 将需求拆成前置条件—交互—后置条件，并通过运行时状态注入验证 | 提供细粒度行为检查的另一条路线 |
| [GameDevBench](https://arxiv.org/abs/2602.11103) | 评测 Agent 对 Godot 游戏项目的开发和修改能力 | 把游戏开发从局部代码任务扩展到项目级任务 |

GameASG-Bench 的位置更具体：**在生成开始前先固定评测接口和可执行检查，让不同内部实现的游戏都能接受同一套行为测试。** 它不要求 Agent 使用某种类名或内部数据结构，但要求公开接口的语义、真实游戏状态和可见行为彼此对应。

## 三、研究问题解读：高检查通过率是否真的代表完成了任务

以下四个问题是我们的阅读归纳，论文在实验部分明确以 RQ1–RQ4 组织：

1. 当需求包含完整玩法循环时，现有 Agent stack 能否完成全部必需行为？
2. 工具权限和名义 turn budget 会怎样影响完成率？
3. 推理强度提高是否稳定带来更多完整任务，额外 token 是否值得？
4. 对同一个模型，换用不同 harness 后，成功的是不是同一批任务？

这些问题要求把“通过了多少个检查”和“有多少个任务所有必需检查都通过”明确分开。后者才更接近一个可交付应用的任务级完成。

## 四、方法解读：先规定可测试接口，再用浏览器证据验证

![GameASG-Bench 的 47 道任务组成：游戏类型、2D/3D 维度和参考技术](../assets/img/blog/gameasgbench/taxonomy.png "图 1 · 三个面板依次展示 47 道任务的类型、空间维度和参考实现技术。来源：原论文 Figure 1；源文件 Figures/taxonomy_genre.pdf、taxonomy_dimension.pdf、taxonomy_technology.pdf，渲染并纵向拼接，未改动图中数据。论文版本：arXiv v1。")

### 第一步：让每道任务同时描述玩法和测试接口

每道任务要求生成一个自包含的浏览器原生游戏，交付文件是 `index.html`。任务包包含三个文档：

| 文档 | 文件 | 作用 |
| --- | --- | --- |
| Generation prompt | `target.md` | 工作区、交付协议和简短玩法目标；由 harness 直接传给 Agent |
| Gameplay design requirement | `game-spec.md` | 目标、控制、实体、状态转移、反馈、终止和重启要求 |
| Evaluation interface specification | `tdd.md` | 场景准备、动作和观察语义、拒绝行为与不变量 |

人类作者在生成前写好场景、动作、快照字段和检查代码；Agent 读取玩法与 TDD 文档，同时实现游戏和评测接口。这样评测器不需要知道游戏内部对象图，只需要知道接口的稳定含义。

### 第二步：用四个接口方法连接“准备—操作—观察”

每个任务通过 `window.__gameTest` 暴露四类能力：

1. `reset` 恢复初始状态并清除临时效果；
2. `loadScenario` 把游戏带到一个可合法到达的中间状态，不能直接制造待测结果；
3. `input` 接收玩家级动作，例如移动单位或选择目标；
4. `getSnapshot` 返回可序列化的相关状态。

关键约束是，接口操作和快照必须作用于驱动可见游戏的底层状态。否则 Agent 可以写出一套自测专用的“假状态”：快照显示成功，画面和真实输入却没有变化。`loadScenario` 允许跳过漫长前置流程，但不允许绕过最终被测动作。

### 第三步：把证据拆成 L1、L2 两层，把要求拆成 P0、P1、P2 三级

L1 检查源代码层面的合规性。共享 runner 读取 HTML 和本地脚本，执行工具检查、正则断言与反模式规则。它能发现接口是否声明、代码是否包含必要结构，但正则命中注释或字符串时，并不能证明玩法真的正确。

L2 在本地服务上用无头 Chromium 运行 `checks.js`。检查按 prepare–act–observe 顺序进行：先加载合法场景，再调用语义动作或发送真实鼠标/触摸输入，最后比较快照、渲染、运行时错误和不变量。每项检查返回 PASS、FAIL 或 NOT_APPLICABLE，且每次检查在新页面中启动。

要求优先级与证据层是两套正交概念：P0 是启动、接口可用和最低运行条件；P1 是核心玩法、交互和不变量；P2 是扩展能力和体验完整度。严格任务成功要求交付有效、评测完成、所有 L1 检查通过，以及所有适用的 L2 P0/P1 检查通过。用公式写就是：

\[
s_g=d_g e_g\prod_{c\in\mathcal{L}_g\cup\mathcal{B}_g}p_{g,c},\qquad
SR(\mathcal{G})=\frac{1}{|\mathcal{G}|}\sum_{g\in\mathcal{G}}s_g.
\]

其中 (d_g) 表示交付有效，(e_g) 表示评测完成，(p_{g,c}) 表示检查 (c) 是否通过。主指标的分母是全部计划任务，包含生成或评测失败的任务；只有在论文明确报告 conditional strict success 时，才改用完成评测的任务作分母。

### 第四步：构建有正例控制的任务集

基准包含 **47 道任务、12 个主要游戏类型**，其中 32 道是 2D、15 道是 3D。参考实现主要使用 Canvas 2D 或 Three.js，但这些技术标签不限制 Agent 的合规实现。整套测试包括 336 个 L1 检查和 885 个 L2 检查，其中 L2 的 P1 核心检查有 534 个。

每个参考实现都先由人工按玩法和 TDD 独立核验，再运行全部 L1 和适用的 L2 P0/P1。47 个参考实现全部通过核心验收，这为检查套件提供了正例控制。任务不要求后端、账号、外部数据库、私有或付费素材，也不要求无限多人网络服务，目的是把问题集中在输入、状态、渲染和玩法逻辑的整合上。

## 五、实验设计与结果：任务级成功远低于检查平均分

### 主实验：九个 Agent stack 的端到端表现

每个任务—配置组合从干净工作区开始运行一次，浏览器视口固定为 1280 × 800。RQ1 比较九个 stack，模型使用各自最大推理强度和完整工具权限；主指标是 47 道计划任务上的 strict task success rate，其他指标是检查通过率。

| 模型 | Harness | 严格成功 | L1 均值 | L2 均值 | L2 P0 | L2 P1 | L2 P2 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| GPT-6-Astra | Codex CLI | **26/47 (55.3%)** | 98.0 | **93.2** | **99.0** | **92.7** | **92.4** |
| Claude-Opus-5 | Claude Code | 24/47 (51.1%) | **99.6** | 90.4 | 91.2 | 89.9 | 91.1 |
| GPT-5.6-Sol | Codex CLI | 21/47 (44.7%) | 98.9 | 91.3 | 100.0 | 89.7 | 91.9 |
| DeepSeek-V4-Flash | Claude Code | 18/47 (38.3%) | 99.4 | 89.3 | 98.0 | 86.7 | 90.2 |
| DeepSeek-V4-Pro | Claude Code | 15/47 (31.9%) | 99.6 | 85.2 | 85.3 | 83.9 | 88.9 |
| Kimi-K3 | Claude Code | 15/47 (31.9%) | 97.7 | 88.5 | 98.0 | 86.3 | 89.7 |
| GLM-5.2 | Claude Code | 11/47 (23.4%) | 98.8 | 84.6 | 91.2 | 83.3 | 83.0 |
| Hunyuan-3 | Claude Code | 10/47 (21.3%) | 98.3 | 81.7 | 96.1 | 78.2 | 82.3 |
| MiniMax-M3 | Claude Code | 7/47 (14.9%) | 98.3 | 70.6 | 91.2 | 64.5 | 75.4 |

*来源：原论文 Table 3，PDF 第 7 页。L1/L2 是检查通过率；strict success 要求同一任务的所有必需检查都通过。*

最重要的结果不是“最高 L2 均值为 93.2%”，而是最高严格任务成功率只有 **26/47 = 55.3%**。GPT-6-Astra 的 L1 均值为 98.0%，但只有 40 个交付物通过全部 L1；单个必需检查失败就会阻止 strict success。GPT-5.6-Sol 的 L2 均值高于 Claude-Opus-5（91.3 对 90.4），严格成功却更少（21 对 24）。这正是平均检查分会掩盖任务级缺陷的例子。

资源也没有简单的“越大越好”关系：Astra 平均输出 55.5k token、26 个严格成功；DeepSeek-V4-Flash 平均输出约 203.6k token，却只有 18 个严格成功。论文报告的每题平均费用中，Astra 为 USD 4.4445，Claude-Opus-5 为 USD 11.8500，DeepSeek-V4-Flash 为 USD 0.2461；这些费用是作者实验中的 API 用量统计，不等于完整复现实验成本。

### 分析一：工具权限与名义 turn budget

固定 DeepSeek-V4-Flash、Claude Code、最大推理强度和 120-turn 基线，作者先改变工具权限。完整工具访问得到 **18/47** 个严格成功；无工具、只读写文件、文件加语法检查分别是 7、6、9 个。完整工具将 L2 P1 通过率提高到 86.7%，但“加语法检查”从 6 个提高到 9 个严格成功时，P1 反而从 66.2% 变成 63.4%，说明成功任务数和 pooled check rate 不必同步变化。

再固定完整工具，改变名义 turn budget：30、60、120 turns 时，完成评测的任务数分别为 10/47、32/47、47/47，严格成功分别为 7、13、18 个。按全部 47 道计划任务计算，成功率从 14.9% 上升到 27.7% 和 38.3%。条件成功率则是 70.0%、40.6%、38.3%。因此预算增加的一个直接作用，是让更多任务完成生成、验证和交付；不能把全计划分母上的增长都解释成代码质量提升。

### 分析二：推理强度存在效率拐点

同样固定模型、harness、工具和 120 turns，低、高、最大推理强度的严格成功分别是 7/47、19/47、18/47。高强度的 19 个成功超过最大强度的 18 个，同时平均推理 token 为 138,232，比最大强度的 189,210 少 **26.9%**。最大强度的 P0、P1、P2 检查通过率最高，但任务级成功率并不单调增加。

这组结果支持一个谨慎结论：更多思考预算可能提高局部检查分，却不保证跨越“所有必需检查都通过”的最后一步。实验是每个配置每题一次，不能由此证明高强度在更多随机种子下都优于最大强度。

### 分析三：相同总成功数，可能是不同的任务集合

DeepSeek-V4-Flash 在最大推理强度、完整工具下分别使用 Claude Code 和 Codex CLI。两个 harness 都是 **18/47 (38.3%)** 严格成功，但只有 **10 道任务**在两者下同时成功；8 道只在 Claude Code 成功，8 道只在 Codex CLI 成功，21 道两者都失败。

资源画像也不同：Codex CLI 平均产物 69.5 KB，对比 Claude Code 的 85.2 KB 小 18.4%；平均输出 token 112.8k，对比 203.6k 少 44.6%。这说明 harness 不只是一个薄薄的命令包装层，它的系统指令、上下文管理、工具 schema、执行协议和端点都可能改变修复路径。总成功数相同，不能说明两个环境等价。

### 分析四：真实输入和场景准备能抓到自测遗漏

论文给出两个诊断案例。GPT-6-Astra 生成的 Diner Dasher 通过 L1 和 L2 P0/P2，但真实鼠标和触摸拖拽不能推动服务进度；问题只有在玩家级输入检查中暴露。DeepSeek-V4-Flash 生成的 Turbo Smash Beast 在自测里通过显式推进时间的路径，但评测先加载场景，再用真实驾驶输入，重置/场景模式抑制了自然时间推进，导致加速和滑行失败。

这些案例回应了方法设计的核心：接口自测能说明“某个调用路径能工作”，真实输入与场景准备的组合才检查“玩家在合法状态中完成动作时，画面和状态一起正确变化”。附录还记录了触摸坐标、隐藏完成界面、未闭合语法、更新循环、Canvas 负半径以及重置状态泄漏等由执行反馈触发的修复。

## 六、我们自己的思考

### 课题思考：这个领域在研究什么

这个方向研究的是从“生成代码”走向“交付完整行为”。GameASG-Bench 把责任拆成三方：人类作者在生成前定义可控动作和可观察语义，Agent 实现接口和游戏，评测器用固定程序执行并报告证据。这样，评测对象不再只是源代码或截图，而是需求、运行时状态、玩家输入和可见结果之间的对应关系。

它还把“正确性”从一个二元标签拆成两条轴：检查通过率告诉我们局部要求完成得怎样，strict success 告诉我们一项任务能否作为整体交付。两者同时报告，才能看见应用级生成中常见的最后一公里问题。

### 局限问题思考：目前还存在哪些问题

第一，L1 正则和接口声明可能被注释或字符串命中，论文也明确承认它们不是玩法正确性的证据。严格成功依赖 L2，但 L2 只执行作者预先写好的动作序列，仍可能遗漏未列出的交互组合。

第二，`NOT_APPLICABLE` 的处理存在协议风险。论文指出当前 runner 没有禁止必需 P1 检查返回 NOT_APPLICABLE；如果任务作者或实现让关键检查被排除，适用检查分母和严格成功解释都会受到影响。

第三，47 道浏览器游戏是一个有边界的代理。它主要测试自包含、有限时长的 2D/3D 游戏，不覆盖后端、账号、多人服务、长时间运行和复杂商业应用；每个任务—配置只跑一次，也无法估计生成随机性的方差。

第四，RQ2–RQ4 主要围绕 DeepSeek-V4-Flash 和两个 harness 展开。工具权限、turn budget、推理强度与运行协议之间仍可能交互，资源成本也只报告可用的 token/API 统计，不能直接换算成完整工程人力。

### 解决方案思考：这些问题有哪些解决方向

对应第一点，可以把源代码检查降级为诊断证据，并增加不依赖 Agent 自报的浏览器状态、渲染差分、输入监听和终态一致性检查；同时对动作顺序和非法操作做系统化组合测试。

对应第二点，应在 runner 中禁止必需 P1 返回 NOT_APPLICABLE，或者将其统一计为失败，并发布每项检查的适用性审计。对关键任务还可以加入隐藏的重启、边界状态和跨页面回归测试。

对应第三点，可以沿同一接口协议扩展到后端服务、持久化应用和多人会话，把一次性任务改成多轮独立生成并报告置信区间。浏览器游戏仍可作为快速回归集，但不应单独代表所有自主软件生成能力。

对应第四点，应在相同模型与 harness 下重复多次，使用配对任务分析差异，并把失败修复、浏览器运行、评测和基础设施成本全部计入。对 harness 的比较还应公开系统指令、工具 schema 和终端协议的可控版本，才能更接近可复现的因果对比。
