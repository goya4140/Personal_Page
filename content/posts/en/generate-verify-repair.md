Generate–Verify–Repair (G–V–R) is a basic loop spanning coding-agent task construction, execution, and training. Systems generate candidate programs or complete executable task bundles, run them in real environments, collect tests, state changes, or process assessments, then use failure evidence to localize and repair code, task descriptions, environments, verifiers, or trajectories. Unlike ordinary post-generation self-reflection, G–V–R requires executable or auditable feedback and clean-state revalidation after repair. The maintained object is therefore the consistent relationship among tasks, environments, verifiers, candidate solutions, and data lineage, beyond final code.

## Generate

Generation constructs objects that can subsequently be executed and verified. Early work generated programs satisfying formal specifications or patches passing tests: Sketch searches implementations for partial programs with holes; CEGIS adds verifier counterexamples to subsequent constraints; GenProg, SemFix, and Angelix generate patches through test-driven search or semantic constraints. [Sketch](https://doi.org/10.1145/1168857.1168907) [CEGIS](https://arxiv.org/abs/1407.5397) [GenProg](https://doi.org/10.1109/ICSE.2009.5070536) [SemFix](https://doi.org/10.1109/ICSE.2013.6606623) [Angelix](https://doi.org/10.1145/2884781.2884807) Modern coding agents extend generation from individual programs to executable bundles containing task descriptions, repository snapshots, dependencies, tests, reference solutions, and interaction traces.

Generation can begin from different trusted seeds. SWE-bench and SWE-Gym construct repository tasks and training environments from real issues/PRs, retaining ecological realism while inheriting public-data contamination, underspecification, and environment drift. [SWE-bench](https://arxiv.org/abs/2310.06770) [SWE-Gym](https://arxiv.org/abs/2412.21139) R2E-Gym generates tests from commits and works backward to task descriptions; SWE-smith first establishes runnable environments, then injects defects that break existing tests. These approaches scale more readily, but risk implementation-hint leakage and mismatch between synthetic defects and real issues, respectively. [R2E-Gym](https://arxiv.org/abs/2504.07164) [SWE-smith](https://arxiv.org/abs/2504.21798)

Further work jointly generates tasks, environments, verifiers, and training traces. SWE-Factory builds and repairs issue-evaluation environments, validating tasks through exit codes and fail-to-pass checks. Terminal-World derives instructions, environments, and teacher trajectories from agent skills. CLI-Universe generates capability-taxonomy blueprints, then filters tasks through Docker, rubrics, hint filtering, and fail-to-pass gates. [SWE-Factory v3](https://arxiv.org/abs/2506.10954v3) [Terminal-World](https://arxiv.org/abs/2605.20876) [CLI-Universe](https://arxiv.org/abs/2606.22883) Meta-Task makes generating terminal tasks an executable task itself; RST uses verified tasks as seeds for recursive generation. [Meta-Task](https://arxiv.org/abs/2607.27929) [RST](https://arxiv.org/abs/2608.05466) Beyond counts, such systems should report build success, candidate rejection, validation pass rates, cost per valid task, and transfer to real tasks. Greater length or difficulty does not automatically imply greater realism.

Generated structure determines which behaviors can be verified and which components can be repaired. Misaligned tasks, environments, and tests make even strong models optimize the wrong problem. Counterexamples, failed tests, and rejection reasons should therefore condition subsequent generation. Repaired bundles should preserve seeds, models, verifier versions, and repair histories to prevent lineage leakage in recursion or dataset splits.

## Verify

Verification determines whether generated objects meet requirements and produces evidence for subsequent decisions. It covers functional correctness and regressions, stable execution, sufficient task specification, acceptance of different valid implementations, and trajectory safety/policy compliance. A verifier is a versioned, calibrated, audited evidence stack rather than an inherently correct oracle.

Formal specifications and executable tests are the most direct checks. Sketch, CEGIS, and semantic repair can return meaningful counterexamples through checkers, symbolic execution, or constraints. HumanEval, APPS, SWE-bench, and most terminal tasks use hidden tests, exit codes, or state changes. [HumanEval](https://arxiv.org/abs/2107.03374) [APPS](https://arxiv.org/abs/2105.09938) Tests automate well, but verify only encoded behavior. UnsatGuided shows that additional generated tests can reduce some introduced regressions, while the oracle problem limits their ability to complete incomplete fixes. [UnsatGuided](https://arxiv.org/abs/1810.10614)

Generated tests, property checks, and learned verifiers can supplement limited human tests. CodeT generates code and tests and ranks candidates by dual execution agreement. Property-Generated Solver uses property-based testing of invariants, reducing dependence on guessed output oracles. [CodeT](https://arxiv.org/abs/2207.10397) [Property-Generated Solver](https://arxiv.org/abs/2506.18315) CodeRanker predicts compilation/runtime errors without execution; LEVER reads tasks, programs, and actual execution results. R2E-Gym shows complementary error modes between executable and execution-free verifiers. [CodeRanker](https://arxiv.org/abs/2206.03865) [LEVER](https://arxiv.org/abs/2302.08468) Coverage and ranking may improve, but common model/data origins for code, tests, properties, and judges can still create correlated errors. Majority voting cannot replace evidence independence.

Final pass/fail labels poorly localize responsibility in long trajectories. Process verifiers assess intermediate actions with rubrics or rewards. SWE-TRACE connects stepwise oracles, process reward models, and test-time pruning; TrajDebug follows error lifecycles, resolution status, and terminal impact to distinguish recovered local mistakes from critical errors causing terminal failure. [SWE-TRACE](https://arxiv.org/abs/2604.14820) [TrajDebug](https://arxiv.org/abs/2608.06346) For safety, AgentDojo evaluates utility and prompt-injection security separately, while AgentSentry uses counterfactual re-execution to locate takeover points in multi-turn tool use. [AgentDojo](https://arxiv.org/abs/2406.13352) [AgentSentry](https://arxiv.org/abs/2602.22724) Outputs should therefore distinguish functionality, regressions, safety, cost, replay stability, and provenance, rather than collapse them into one score.

Verification both gates acceptance and guides repair. A failure label alone is insufficient: evidence should identify components, steps, or state changes. Generation should avoid candidates, tests, and judges sharing identical biases. Since repair may alter tests, environments, or policies, reacceptance requires a fixed verifier version and renewed false-acceptance/false-rejection checks on reference solutions, independently valid implementations, near misses, and adversarial shortcuts.

## Repair

Repair converts verification failures into bounded state changes. Targets include code/patches, task descriptions, dependencies, tests/graders, contextual memory, action interfaces, and model policies. Some failures warrant local repair, others reranking; failures that invalidate task identity or lineage may require regeneration or rejection. The central decision is which component or causal branch produced the failure and which minimal replayable modification addresses it.

Candidate programs can be repaired with test feedback, semantic constraints, or tool evidence. SemFix, DirectFix, and Angelix derive repair constraints while preserving program structure. Self-Debugging and CRITIC revise outputs using execution or external tools. Agentless fixes repository repair into localization, repair, and patch-validation stages to reduce unproductive exploration. [DirectFix](https://doi.org/10.1109/ICSE.2015.63) [Self-Debugging](https://arxiv.org/abs/2304.05128) [CRITIC](https://arxiv.org/abs/2305.11738) [Agentless](https://arxiv.org/abs/2407.01489) SEIDR explicitly compares repair-focused, replace-focused, and hybrid strategies, showing that repairing versus replacing a candidate is itself an evaluable routing decision. [SEIDR](https://arxiv.org/abs/2503.07693)

Repair can also target trajectories, context, and data. Reflexion stores feedback in episodic memory to change subsequent trials. PromptArmor detects/removes potential injections before agent processing. CompactionRL jointly learns execution and history compression for trajectories exceeding context windows. [Reflexion](https://arxiv.org/abs/2303.11366) [PromptArmor](https://arxiv.org/abs/2507.15219) [CompactionRL](https://arxiv.org/abs/2607.05378) These approaches risk deleting useful evidence or persistently storing incorrect reflections. Context repair should therefore be judged by whether fault localization and repair decisions remain reproducible after compression or sanitization, beyond compression ratio or fluency.

Failure/repair traces can become training signals. DAgger requests expert correction on states actually visited by the learner. ETO pairs failed trajectories with better continuations. DPO and DMPO support single-turn and multi-turn preference optimization. [DAgger](https://proceedings.mlr.press/v15/ross11a.html) [ETO](https://arxiv.org/abs/2403.02502) [DPO](https://arxiv.org/abs/2305.18290) [DMPO](https://arxiv.org/abs/2406.14868) A failed trajectory should not be labeled negative in its entirety: valid prefixes, failure evidence, and successful recovery can remain valuable. A better structure retains the bad action, failure observation, diagnosis, and repaired sibling from the same starting state, supporting bad-action loss masking, recovery SFT, preference learning, or process rewards as appropriate.

Repaired states must return to execution and verification rather than be accepted directly. Changes to prompts, environments, or verifiers also require checking task-identity drift, relabeling needs, and train/test lineage. The complete loop is `versioned generation → independent verification → component/causal diagnosis → targeted repair or discard → clean replay → adversarial audit → freeze and lineage`. What remains optimized is the valid relationship among tasks, environments, verifiers, solutions, and trajectories, beyond adaptation to fixed tests.
