Collected domain documents, repositories, API documentation, user traces, tutorials, and workflow specifications are usually not directly usable for agent training. Task, action, state, and verification structures must be added to meet the requirements of pretraining, supervised fine-tuning (SFT), and reinforcement learning (RL). We describe this as instruction formation, action structuring, environment construction, and reward construction. Pretraining, SFT, and RL are not categories parallel to those four steps: normalized materials can support pretraining; instructions and actions mainly produce SFT data; environments and rewards further provide interactive experience for RL.

## Instruction formation

This converts documents, issues, tutorials, or business specifications into explicit tasks, separating model-visible context, hidden environment state, and verifier-private information. Pretraining materials may retain sequences of documents, code, schemas, or weakly annotated traces, emphasizing provenance, versioning, deduplication, and licensing. SFT instead requires adequately specified instruction–response examples. Including reference patches, hidden tests, or complete operational answers in inputs leaks labels; omitting permissions, historical state, or success conditions makes tasks underspecified.

[Self-Instruct](https://arxiv.org/abs/2212.10560) illustrates automatic generation of instructions, inputs, and outputs from a few seeds, but heuristic filtering does not establish factual correctness. [SWE-bench](https://arxiv.org/abs/2310.06770) extracts tasks from real GitHub issues and preserves execution context through a base commit, repository, and tests. [DIVE](https://arxiv.org/abs/2603.11076) takes an evidence-first approach: execute real tools to obtain evidence, then generate supported tasks, reducing synthetic requests that mismatch tool capabilities or lack verifiable answers. Instruction formation therefore establishes relationships among tasks, evidence, and information boundaries, beyond rewriting text.

## Action structuring

This converts final answers or procedures into learnable action interfaces and trajectories. For tool agents, SFT labels should include tool selection, arguments, returns, and dependencies across turns, beyond textual answers. [Toolformer](https://arxiv.org/abs/2302.04761), [API-Bank](https://arxiv.org/abs/2304.08244), and [ToolLLM/ToolBench](https://arxiv.org/abs/2307.16789) illustrate tool-call bootstrapping, executable training/evaluation, and large-scale API-path synthesis. [APIGen](https://arxiv.org/abs/2406.18518) adds format, execution, and semantic checks to move synthetic calls from syntactic validity to executability and task agreement.

Real workflows also include clarification, user changes, and tool dependencies. [APIGen-MT](https://arxiv.org/abs/2504.03601) separates ground-truth actions from multi-turn dialogue; [TOUCAN](https://arxiv.org/abs/2510.01179) generates multi-tool, multi-turn traces from real MCP environments. Tutorials and user logs can become GUI demonstrations, but must replay from corresponding states. An expert’s or tutorial’s successful path is not the only valid path. These data mainly support SFT; minimum requirements include parseable actions, temporal consistency, clear positive/negative labels, and no future information inserted into earlier observations.

## Environment construction

This places fixed trajectories back into interactive worlds, supplying initial states, action execution, state transitions, exceptions, side effects, and reset. SFT imitates existing demonstrations, whereas RL must try different policies and observe consequences. A sequence of tool calls or static returns alone is therefore not RL data. [ALFWorld](https://arxiv.org/abs/2010.03768), [WebShop](https://arxiv.org/abs/2207.01206), and [InterCode](https://arxiv.org/abs/2306.14898) provide step–observation–reset interfaces for embodied, web, and code tasks. [AppWorld](https://arxiv.org/abs/2407.18901) checks both target states and collateral damage, accepting multiple policies rather than matching one reference trace.

Recent work scales environments automatically. [AgentGym](https://arxiv.org/abs/2406.04151) unifies heterogeneous interfaces; [EnvScaler](https://arxiv.org/abs/2601.05808) programmatically generates environment skeletons, scenarios, and rule validators; [EnvFactory](https://arxiv.org/abs/2605.18703) explores executable environments from real resources. In software engineering, [SWE-Gym](https://arxiv.org/abs/2412.21139), [SWE-smith](https://arxiv.org/abs/2504.21798), and [MEnvAgent](https://arxiv.org/abs/2601.22859) organize repositories, dependencies, containers, and tests into replayable tasks. Quality should include state-graph coverage, tool combinations, exceptional branches, reset success, and versions, beyond environment counts.

## Reward construction

Success conditions, progress, side effects, and policy constraints become verifiers and rewards that produce RL signals. Basic checks cover format and execution; stronger checks assess target states, damage to unrelated state, semantics, and policy compliance. [HumanEval](https://arxiv.org/abs/2107.03374) uses unit tests for functional correctness; SWE-bench combines fail-to-pass and regression tests; AppWorld checks targets and collateral damage; [PaperBench](https://arxiv.org/abs/2504.01848) combines program execution, fresh reproduction, and hierarchical rubrics.

Terminal rewards are stable but sparse, so long trajectories also need reliable process signals. [Verifiable Process Rewards](https://arxiv.org/abs/2605.10325) uses symbolic or algorithmic intermediate oracles for turn-level rewards. [COVERT](https://arxiv.org/abs/2604.09813) adds distractors, ambiguous requests, and incorrect tool outputs while preserving the oracle. [Envs-FORGE](https://arxiv.org/abs/2608.14312) adjusts environment difficulty using current-policy pass rates and verifier rewards. These methods extend RL data from static traces to environment–rollout–verifier combinations, while making verifier bias central: shared task-generator/verifier origins, or rewards that accept only a reference path, may teach exploitation rather than real workflow competence.

| Step | Added structure | Main training uses | Core quality requirements |
|---|---|---|---|
| Instruction formation | Tasks, context, information boundaries | Domain pretraining, instruction SFT | Clear sources and versions; sufficient specification; no answer leakage |
| Action structuring | Tool schemas, actions, trajectories | Tool-use / GUI / multi-turn SFT | Parseable, executable, temporally consistent actions |
| Environment construction | Initial states, transitions, exceptions, reset | Replay, offline/online RL | Realistic, resettable state; side-effect checks |
| Reward construction | Verifiers, rewards, policy constraints, budgets | RL, curricula, failure recovery | Independent checks; equivalent valid paths accepted; resistance to reward hacking |

The four steps form a data-transformation chain with feedback. Instructions and actions provide SFT task and behavior supervision; environments and rewards extend this into explorable, verifiable RL experience. Failed RL rollouts can be localized, repaired, and rerun, returning as SFT repair traces or recovery environments. Pretraining provides domain/tool knowledge, SFT initializes stable action, and RL learns long-term consequences and recovery, within a common processing framework.
